# 专业版行记录格式要点

以下为固定上游格式技能的重述，适用于该修订覆盖的专业版格式。完整字段必须逐项查询官方类型索引、文档、图元 Schema；此摘要不能作为完整格式生成器。

## 记录边界与判优

一条记录由 JSON 外壳、双竖线分隔符和载荷组成，记录末尾再附一个竖线与 LF。不要用 CRLF 替换，也不要按单个竖线简单 split 全文件。

外壳包含 type、ticket；一般原子还有 id。DOCHEAD 外壳没有 id。普通原子与单例、FONT、BLOB 的 id 规则不同，不能全部生成随机 ID。

同一文档内按归一化 id 比较记录，type 不构成独立比较键。较大 ticket 胜出；ticket 相同则比较文档头 client，字典序较大者胜出。旧 2.0 文档对 client 的方向与此修订实现不同。不要用旧规则“修复”3.0 数据。

## 删除语义

删除普通原子通过追加空载荷记录表达；删除整个文档使用 DELETE_DOC 的 isDelete 标志。这两种载荷不能互换。META 的消费者需要对象字段，不能用空载荷假装删除 META；INSTANCE_ATTR 的空载荷则有删除属性的含义。协作中的 pend/revoke 状态不适合凭静态摘要重写。

## 文档头、画布与关联

每个文档先写 DOCHEAD。只有具有画布的文档才需要 CANVAS；BOARD、DEVICE、CONFIG、SCH 等不要机械增加 CANVAS。client 和 uuid 按该修订的 16 位小写十六进制约束核对。

同名 LINE 等图元在 SCH_PAGE 和 PCB 的字段不同。校验时使用 `PCB_LINE` 一类带文档前缀的类型，或明确 `--doc PCB`；不能让裸类型名称落到错误的默认 Schema。

按照“查询类型 → 阅读文档/图元 → 核对关联 → 生成 → 校验 → 存档”执行。关联关系包括导线分组、属性、库引用等；单个图元字段合法并不能证明其关联齐全。

## 工具边界

本包现已附带官方 validate.js、全量 Schema、图元说明和样例，使用 [包内资源](bundled-official.md) 指定的隔离依赖入口。校验器必须覆盖全部生成图元，失败时修正输入；不得通过删掉必要字段或换错文档类型获得绿灯。最终仍需目标客户端打开、网表回读与 DRC。
